# AWS high availability, disaster recovery and cost — the working behind chapter 17

**Date:** 2026-08-29
**Question:** if this platform had to be highly available, redundant and fault
tolerant on AWS, what does each tier become, what does the repository's own code
force, and what does it cost?
**Status:** analysis only. **There is no AWS account and nothing here has been
deployed, benchmarked or costed against one**
([Q9](2026-08-26-v3-requirements-clarification.md#q9--scale-target)). Every cost
figure is a list-price estimate with a URL and a fetch date, not a measurement.

[`../architecture/17-scale-out-path.md`](../architecture/17-scale-out-path.md)
aggregates the conclusions. This note carries the working: every option
considered per tier, the failure-mode inventory, the capture active-active
analysis in full, the Iceberg cross-region findings with sources, the RPO/RTO
reasoning, and the raw pricing fetch log.

### 2.1 What the inventory says that the per-tier table does not

Three of the nine rows are not fixed by choosing a managed service:

- **F3** is a design decision about sequence continuity, argued in §4.
- **F5/F7** are a single-writer assumption that a redundant substrate makes
  *more* dangerous, not less, because the substrate will happily run two.
- **F6**'s RTO is a rebuild duration nobody has measured at scale.

Everything else is bought.

## 3. F5 in full: why ingest mid-commit is already idempotent, and what breaks

### 3.1 The mechanism, precisely

[ADR-022](../adr/ADR-022-exactly-once-via-snapshot-offsets.md) stores the
consumed Kafka offsets **inside the Iceberg snapshot summary of the commit that
wrote the rows** — `snapshot-property.k2.kafka-offsets` — rather than in a
separate position store. Three consequences follow, and all three are what make
a mid-commit death safe:

1. **There is exactly one durable fact after any crash.** Either the snapshot
   exists, in which case both the rows and the offsets that produced them are in
   it, or it does not, and neither is. An Iceberg commit is atomic and the
   summary is part of it, so the two cannot disagree. There is no ordering to
   get right and no `status` column to be wedged in.
2. **Crash before the commit is a no-op with orphans.** The Parquet files are
   written and referenced by no snapshot, so no reader sees them; the next run
   reads the same `startingOffsets`, re-reads the same records, writes new files
   and commits. `remove_orphan_files` reclaims the space with a 24 h floor so it
   cannot race a live write (`docker/lake/maintenance.py`).
3. **Crash after the commit is indistinguishable from success.** The commit *is*
   the completion signal; there is nothing left to do after it.

The offset is also the right *type* for this: an offset has an exact successor,
so `endingOffsets` of run *n* is `startingOffsets` of run *n+1* with no gap and
no overlap. A timestamp watermark — what v2 used — has neither property and
needs a lateness buffer, which is a choice between duplicates and loss with no
way to detect which you got.

**None of this depends on what launched the job.** That is the whole reason
chapter 17 can say `docker exec k2-spark-iceberg` becomes an EMR Serverless job
submission and nothing else changes: exactly-once is a property of the commit,
and EMR Serverless commits the same way.

Two supporting rules that also survive the move unchanged:

- `failOnDataLoss=true` on the Kafka read, so a `startingOffsets` below the
  partition's earliest surviving offset is a loud failure and a recorded
  `offset_gap` row in `audit.checks`, never a silent hole.
- The offset reader takes the *latest snapshot whose summary contains
  `k2.kafka-offsets`*, not the latest snapshot, because compaction and expiry
  commit snapshots that carry no offsets (`docker/lake/offsets.py`, unit-tested
  in `tests/test_lake_offsets.py`).

### 3.2 What does break: the lock is host-local

`docker/lake/lock.py` is 30 lines of stdlib:

```python
LOCK_PATH = os.environ.get("K2_LAKE_LOCK", "/tmp/k2-lake-ingest.lock")
fcntl.flock(handle.fileno(), fcntl.LOCK_EX | (0 if blocking else fcntl.LOCK_NB))
```

`ingest.py` takes it non-blocking and exits 2 if held (`ingest.py:500`);
`maintenance.py` takes it blocking and holds it for its whole run
(`maintenance.py:757`). On one host with one Spark container that is an exact
guard: two writers are unrepresentable.

**On EMR Serverless every job run is a fresh container with its own `/tmp`, so
the `flock` is a no-op across runs.** The lock still prevents two writers inside
one job; it prevents nothing between two jobs. And ADR-022's own consequence
table says what that costs:

> **Without the lock there would be duplicates**, and not because Iceberg fails
> to notice: measured on a scratch table with this DDL's
> `commit.retry.num-retries=10`, two identical 5-row appends raised nothing and
> left 10 rows in two append snapshots. Iceberg's optimistic concurrency detects
> the conflict and its retry re-applies the loser on the new base — which is
> correct for an append and fatal for an append that also carries the reader's
> position.

So the residual risk in F5 is exact: after the move, `concurrency_limit=1` on
the Prefect deployment is the *only* thing standing between the lake and a
duplicated ingest window, and it covers only Prefect-launched runs — not the
runbooks, the chaos scripts, `make lake-verify`, or an operator's hand-run
during an incident, all of which dispatch directly today.

**Options considered for replacing it:**

| Option | Verdict |
|---|---|
| Point `K2_LAKE_LOCK` at shared EFS | rejected. `flock` over NFS is advisory-at-best and its failure mode is silent — the worst possible property for a guard whose whole job is to be exact |
| DynamoDB conditional put with a TTL lease | the honest replacement. A conditional write is genuinely atomic across regions; the lease TTL bounds a dead holder. Costs a table and a code change in `lock.py` only |
| Rely on Iceberg's optimistic concurrency | rejected, for the reason ADR-022 measured: the retry is *correct for an append* and therefore silently wrong for an append that carries the reader's position |
| Make ingest single-flighted by construction (one long-lived job) | rejected: it re-introduces the resident streaming runtime ADR-004 removed |

`lock.py` is already env-driven and pure stdlib with no pyspark import, so the
swap is one module. Recording it here means the migration meets it as a known
task rather than as an incident.

## 4. Capture HA: active-active vs active-passive, in full

### 4.1 What ADR-019 actually says

[ADR-019](../adr/ADR-019-rust-capture-tier.md)'s Decision is a binary "run once
per exchange, carrying trades and L2 book on one connection each", and its first
reason states the property:

> One socket per exchange means one sequence space, one reconnect policy, and
> one place where the book and the trades agree about time.

That sentence is about *sequence continuity and book state*, not about process
count. It is the constraint both options below have to survive.

### 4.2 The hook that already exists

Every record carries a `conn_id`: a v4 UUID minted per connection at
`services/capture-rust/src/main.rs:431`, stamped into `TradeRecord`,
`BookSnapshotRecord` and `RawMessageRecord` (`record.rs:68,89,100`) and carried
through silver (`silver.py:160`) into `gold.book_state`, whose identifier fields
are `(exchange, symbol, conn_id)` (`lake.sql:1224`). `conn_msg_seq` is a
per-connection counter alongside it.

**The archive already models "which connection said this".** Two live
connections per venue are *representable* in the schema as it stands. The
question is only what the layers above do with them.

### 4.3 Option A — active-active: two tasks per venue, different AZs, both producing

Traced layer by layer against the code:

| Layer | What happens with two live connections | Verdict |
|---|---|---|
| `raw.messages` | both connections' frames archived verbatim, each row carrying its own `conn_id` in the payload. The "verbatim" promise is **untouched** — it promises the bytes are the venue's bytes, not that there is one copy of each event | **safe**, at 2× raw bytes |
| Bronze | identifier fields are `src_topic, src_partition, src_offset` (`lake.sql:147` and five siblings) — Kafka coordinates. Two producers write different offsets for the same venue event, so the `duplicate_identifiers` audit passes and bronze holds both | **safe by construction**; bronze is a pure function of raw and stays one |
| Silver trades | `silver.score()` computes `venue_replay` over `Window.partitionBy("symbol", "trade_id")` ordered by `(recv_ts_ns, src_partition, src_offset, src_index)` — **`conn_id` is not in that window** (`silver.py:197-200`). The second connection's delivery of the same `trade_id` is therefore scored `venue_replay = true` today, with no code change | **already deduplicated**, bounded by `LOOKBACK = timedelta(days=1)` (`silver.py:56`) |
| Gold trades | `_project_silver` filters `~venue_replay` (`gold.py:75`) and the identifier is `(exchange, canonical_symbol, trade_id)` (`lake.sql:628`), asserted nightly | **safe**; one row per logical trade, unchanged |
| Silver/gold **books** | `books.py` repartitions by `(symbol, conn_id)` and carries per-`(symbol, conn_id)` state in `gold.book_state`; the [ADR-027](../adr/ADR-027-book-snapshot-and-sequencing.md) sampler emits one row per second **per connection**. `gold.book_top20` and `gold.bbo_1s` are keyed `(exchange, canonical_symbol, second)` (`lake.sql:1137,1181`) | **breaks.** Two live `conn_id`s produce two rows per symbol-second and the `duplicate_identifiers` audit fails every run |
| Replay | `scripts/replay_export.py:frames()` refuses a frame set whose `conn_msg_seq` is not `1..n` unbroken — and the check is **scoped to one `conn_id`**. Two connections are two independent `1..n` sequences | **unaffected.** Each exports and replays exactly as today |

The replay row is worth stating positively, because it is the objection one
expects and it does not hold: active-active does not break the contiguity check.
It doubles the number of replayable connections and raises a *different*
question — which of two connections is the authoritative record of a moment —
which is a research-fidelity question, not a mechanical one.

**Where active-active actually costs:**

1. **Books need a cross-connection winner rule.** Something must decide, per
   `(symbol, second)`, which connection's book state is canonical. Every candidate
   rule is a judgement: lowest `recv_ts_ns`, the connection with `checksum_ok`,
   the connection with no `seq_gap` in the window, a stable preference for AZ-A.
   `gold.py`'s docstring says gold is "a projection of silver, not a second
   deduplication with its own rules" — a winner rule is exactly a second
   deduplication with its own rules, in the layer whose design principle is that
   silver already decided.
2. **2× raw forever.** `raw.messages` is 6.47 GB/day of the lake's predicted
   13.6 ([capacity model §4c](../architecture/15-capacity-model.md)) and 48 % of
   its growth, and nothing deletes it. Doubling it doubles the only monotonically
   rising line on the cost sheet — 12.94 GB/day at 1×, 2.59 TB/day at 200×.
3. **2× venue connections.** Public venues rate-limit connections per IP and per
   account. Two full subscriptions per venue is a venue-relations question this
   note cannot answer from here.
4. **Downstream dedup is bounded by a lookback.** Trades dedup for free *within
   one day* (`LOOKBACK`). Two connections whose deliveries straddle that window —
   a long partition, a replayed backlog — stop deduplicating, silently.

### 4.4 Option B — active-passive with health-check failover

One live connection per venue, a standby task in another AZ, promotion on health
check failure. The cost is a gap of N seconds per failover, and the gap is loss:
public WebSocket feeds do not replay and there is no spill-to-disk (ch. 16
blast-radius legend).

**What N is made of**, with the one component this repo has measured:

| Component | Estimate | Basis |
|---|---|---|
| detection | 15–120 s | **measured 119 s** for `CaptureDown` at `for: 2m` (ch. 16). A task-level ECS health check at 3 × 10 s would be ~30 s — design target, not measured |
| task start + WS connect | 3–10 s | **measured 3 s** to a scrapeable target after `docker compose up -d` (ch. 16) |
| subscribe + book resync | seconds to tens of seconds | venue-dependent; Kraken awaits a resync snapshot after a checksum mismatch (`resync.rs`, PR #119) |

So ~35–60 s on a tuned health check, ~2 min on the alert path as configured
today. **And it is recorded, not silent**: the promoted task mints a new
`conn_id` and starts at `conn_msg_seq = 1`, so the archive shows a connection
boundary rather than a continuous stream with a hole in it, and silver's
`seq_gap` / `missing_before` flags score the venue-sequence discontinuity across
the seam.

### 4.5 Recommendation, and what ADR-019 would need to say

**Recommend Option B, active-passive**, for one reason that the trace makes
concrete: active-active is *free* for trades and *broken* for books, and books
are the harder half of the platform. Trades deduplicate today with no code
change because `venue_replay` is scored per `(symbol, trade_id)` with no
`conn_id` in the window; books cannot, because the 1 Hz sampler is per-connection
by construction and the canonical book tables are keyed by second. Buying an
avoided ~40 s gap with a cross-connection winner rule in gold is paying in the
platform's most load-bearing invariant for a bounded, recorded, alertable loss.

**ADR-019 needs no change to adopt Option B.** Its wording is "one socket per
exchange", and under active-passive exactly one socket is live at any instant;
the standby holds no connection. The ADR is already satisfied.

**If Option A were ever taken, ADR-019 would need an appended `Outcome`
recording:** that reason 1's "one socket per exchange" becomes *one
**authoritative** socket per exchange at a time*; that the authority is decided
per `(symbol, second)` in gold and the rule is named there; and that "one place
where the book and the trades agree about time" is now a chosen place rather
than a structural one. That is a materially weaker property, which is the
argument against it stated in the ADR's own terms.

**Revisit trigger for this recommendation:** a measured failover gap above 60 s,
or a venue whose reconnect + resync exceeds it on its own.

## 5. Per tier: managed vs self-managed on EKS

The question per tier is not "which is better" but **what does HA actually cost
in operational surface**, and the tiebreak used throughout is: *a single
maintainer does not run a consensus system he did not have to run.* Every option
below was considered; the pick and its reason are in the last column.

Each "what the repo changes" note is checked against
[`docker/lake/spark_conf.py`](../../docker/lake/spark_conf.py), which reads every
endpoint, region, path-style flag and catalog URI from the environment with the
single-host value as its default.

### 5.1 Capture — ECS Fargate vs EKS

| Option | HA mechanism | For | Against |
|---|---|---|---|
| **ECS Fargate** | one task per venue, `desiredCount=1` per venue, subnets in ≥ 2 AZs; ECS restarts a failed task in a healthy AZ | no nodes to patch, no cluster to run, per-second billing on a tiny footprint. The whole tier is 0.074 CPU / ~0.26 GB predicted across three venues (capacity model §3b, §5) | no node-level control; the per-vCPU-hour rate is above EC2 for a tier that runs 24/7 |
| Capture on EKS | a Deployment per venue with a pod anti-affinity rule | one control plane for everything; cheaper at scale | an EKS cluster — control plane, nodes, CNI, upgrade treadmill — to run three processes that use a fifteenth of a core |
| EC2 with an ASG | ASG min=max=1 per venue per AZ | cheapest | you are now patching AMIs to run a static binary |

**Pick: ECS Fargate.** The tier is three long-lived single-threaded processes
with no local state. Everything an orchestrator offers beyond "keep one of these
running, in some AZ" is unused, and Fargate charges least for the unused parts.

**Repo change:** `K2_BROKERS`, `K2_SCHEMA_REGISTRY_URL`. Both already env-driven
in the capture binary; the image is unchanged.

### 5.2 Bus — MSK vs Redpanda Cloud vs Redpanda on EKS

| Option | HA mechanism | For | Against |
|---|---|---|---|
| **Amazon MSK (provisioned)** | 3 brokers across 3 AZs, `replication.factor=3`, `min.insync.replicas=2`, rack-aware placement | AWS patches and replaces brokers; IAM auth; a published price (§9) | JVM Kafka's operational shape, and the partition arithmetic of chapter 17 §3 still applies |
| MSK Serverless | AWS-managed partitions and capacity | no capacity planning at all | priced per partition-hour (§9), which punishes exactly the high partition counts this design wants at 200× |
| Redpanda Cloud | vendor-managed, multi-AZ | the same engine the repo runs today, so zero behavioural surprise | **quote-based** — the per-unit rates are not published (§9), so it cannot be costed here |
| Redpanda on EKS | StatefulSet, 3 replicas, pod anti-affinity, EBS per broker | cheapest at scale; same engine | you now operate a Raft cluster, its storage and its upgrades, single-handed. Precisely what the tiebreak refuses |

**Pick: MSK provisioned.** It is the only option that is both multi-AZ by
configuration and publicly costable, and Kafka-protocol compatibility means the
producer and the Spark reader do not care that the engine changed. Redpanda
Cloud would be reconsidered the moment a quote exists.

**Repo change:** `K2_BROKERS`, plus SASL/IAM on the producer and on Spark's Kafka
reader. **And one real code change:** capture's producer must set `acks=all`, or
`min.insync.replicas=2` buys nothing. That is a repo edit, not an endpoint swap.

### 5.3 Schema registry

| Option | HA mechanism | For | Against |
|---|---|---|---|
| **AWS Glue Schema Registry** | regional managed service | free — *"Usage of the AWS Glue Schema Registry is offered at no additional charge"* (§9) — IAM-native, no instance | a different client from the Confluent-protocol one the Rust crate uses today |
| The registry MSK or Redpanda Cloud ships | vendor-managed | protocol-identical to today | tied to the bus choice |
| Confluent Schema Registry on ECS | 2 tasks over the `_schemas` topic | protocol-identical, self-hosted | another service to run for a component that serves a handful of schema ids |

**Pick: whichever registry the bus ships, with Glue as the fallback.** The reason
is the shape of the dependency, not the service: `BACKWARD_TRANSITIVE` is a
registry *setting*, and the Avro contracts and the fixed-point `int64` @1e-8 rule
([ADR-020](../adr/ADR-020-avro-fixed-point-contracts.md)) are the interface. A
record is decoded by schema id and the id is in the payload, so the registry is a
lookup table with a strong compatibility rule — not a place to spend HA effort.

**Repo change:** `K2_SCHEMA_REGISTRY_URL` and the registry client's auth. Glue
would additionally change the Rust client library, which is why it is the
fallback rather than the first pick.

### 5.4 Object store — S3

No options table: there is one answer. S3 Standard is already multi-AZ within a
region, so the lake's storage tier is the only tier that is HA with no design
work at all. The interesting questions are **lifecycle** (chapter 17 §5) and
**cross-region** (§6 below), not availability.

**Repo change:** `K2_S3_ENDPOINT` unset (or a VPC endpoint), `K2_S3_REGION` set
to the real region, `K2_S3_PATH_STYLE=false` for virtual-hosted addressing. Plus
one deletion: `MINIO_ROOT_USER` / `MINIO_ROOT_PASSWORD`, read at
`spark_conf.py`'s `lake_session()`, become an IAM task role and stop being passed
at all.

### 5.5 Catalog — Lakekeeper on ECS + RDS vs Glue vs Lakekeeper on EKS

| Option | HA mechanism | For | Against |
|---|---|---|---|
| **Lakekeeper on ECS + RDS Multi-AZ** | 2+ stateless ECS tasks behind an ALB; all state in RDS, synchronously replicated | the REST protocol is unchanged, so Spark, DuckDB and ClickHouse keep addressing tables exactly as today ([ADR-023](../adr/ADR-023-lakekeeper-rest-catalog.md)). Lakekeeper is stateless, so HA is "run two" | you run Lakekeeper; RDS failover is 1–2 min of no commits |
| AWS Glue Data Catalog | fully managed, regional | nothing to run; IAM-native; and cheap — 1 M objects and 1 M requests a month are free (§9) | **not** an Iceberg REST catalog. It is a catalog-*type* change in `spark_conf.py` and an `ATTACH` change in every notebook, and it drops the one property ADR-023 bought: one protocol every engine speaks |
| Lakekeeper on EKS | Deployment + RDS | same as ECS, on a cluster you already have | only if EKS exists for other reasons |

**Pick: Lakekeeper on ECS + RDS Multi-AZ.** Glue is the cheaper and simpler
service and it is still not the pick, because ADR-023's whole argument is
readable-from-anywhere table locations through *one* protocol, and Glue makes the
catalog an AWS-shaped dependency that DuckDB and ClickHouse then have to be
taught separately. The stateless-app-plus-managed-database shape is where the HA
actually lives, and Lakekeeper already has it.

**Repo change:** `K2_LAKE_CATALOG_URI`, `K2_LAKE_WAREHOUSE`, catalog auth — all
three already environment variables in `spark_conf.py`.

### 5.6 Ingest and maintenance — EMR Serverless vs Spark on EKS

| Option | HA mechanism | For | Against |
|---|---|---|---|
| **EMR Serverless** | AWS runs the workers; a failed job is a retry, and ADR-022 makes a retry safe (§3.1) | billing matches the shape exactly — 288 short jobs a day plus one nightly window, no idle cluster | cold start per job; **and it takes the `flock` away** (§3.2) |
| Spark on EKS | driver and executors as pods, restart on node loss | one cluster for everything; a shared volume could host the lock file | an EKS cluster, a Spark operator, and node capacity sized for a burst that happens for ~90 s every 5 minutes |
| EMR on EC2 | a persistent cluster | familiar | a 24/7 cluster for a duty cycle in the single-digit percent |

**Pick: EMR Serverless**, with §3.2's lock replacement as an explicit
precondition rather than a footnote. The tier's entire dispatch change is one
line — `docker exec k2-spark-iceberg python3 …` becomes a job submission — and
`ingest.py`, `offsets.py`, `maintenance.py` and the offsets-in-snapshot mechanism
are untouched, because exactly-once is a property of the Iceberg commit and not
of the launcher.

**Repo change:** the Prefect deployment's dispatch, and `docker/lake/lock.py`.
Nothing else.

### 5.7 Hot tier — ClickHouse Cloud vs ClickHouse on EC2/EKS with replicas + Keeper

| Option | HA mechanism | For | Against |
|---|---|---|---|
| **ClickHouse Cloud** | compute is stateless over object-backed storage; the vendor runs replication | no Keeper ensemble to operate. The tier originates nothing (ADR-025), so getting this wrong costs a rebuild, not data | **no published per-unit rate** (§9). Version control becomes the vendor's, which matters given ADR-015 pinned 24.3 LTS for JDBC compatibility |
| ClickHouse on EC2, `ReplicatedMergeTree` × 2 + 3-node Keeper | Keeper consensus; replicas across AZs | full version control; publicly costable | **five instances** and a consensus ensemble, for a tier whose recovery story is already "reload from the lake" |
| ClickHouse on EKS via the operator | the same, in pods | the operator automates the Keeper wiring | an EKS cluster plus the operator's own semantics |
| **Single node + fast rebuild** | none; recovery is a reload | matches ADR-025's contract exactly: derived, rebuildable, originating nothing | an outage is a full rebuild, and the rebuild is unmeasured at 200× |

**Pick: ClickHouse Cloud if a quote lands inside the storage line's noise;
otherwise two `ReplicatedMergeTree` replicas plus a 3-node Keeper ensemble on
EC2.** The reason is worth stating plainly: **this is the only tier where the
honest answer is "measure the rebuild first".** ADR-025 already makes the tier
derived and rebuildable, so if the rebuild is fast enough the correct amount of
HA here is *none*, and the money belongs in the lake instead. The design does not
know that number, and picking without it would be the kind of unfounded claim
this repository's rules exist to prevent.

**Repo change:** connection strings, and the `iceberg()` rebuild path gains an S3
URL and an IAM role instead of MinIO keys. The contract — reload by pull through
`iceberg()`, the `s3()` glob banned — is unchanged.

### 5.8 Orchestration — Prefect Cloud vs self-hosted

| Option | HA mechanism | For | Against |
|---|---|---|---|
| **Prefect Cloud** | vendor-run control plane; workers run in your account | deletes three containers and a database from the HA problem, including the RDS instance behind them. Published price: Starter $100/mo, Team $100/user/mo (§9) | the control plane becomes a third party in the ingest path |
| Prefect server + worker on ECS + RDS Multi-AZ | 2 server tasks, RDS Multi-AZ, workers in ≥ 2 AZs | the same containers as today, publicly costable | you run it |

**Pick: self-hosted on ECS + RDS Multi-AZ**, for one reason that is not about
Prefect: after §3.2, `concurrency_limit=1` on the `lake-ingest-5min` deployment
(`docker/lake/flows/deploy_lake.py:55`) is load-bearing for *correctness*, not
merely for politeness. A correctness-critical setting belongs in an account you
control until the distributed lock replaces it — at which point Prefect Cloud
becomes the obvious pick and this row should be revisited.

**Repo change:** the API URL and the work-pool type. The flows, the schedules and
the concurrency limit are unchanged.

### 5.9 Observability — AMP/AMG vs self-hosted

| Option | HA mechanism | For | Against |
|---|---|---|---|
| **AMP + AMG** | managed, regional, multi-AZ | Alertmanager finally exists — the single host has none — and the metric names, the 28 alert rules, the `runbook:` annotations and the promtool tests all move unchanged | per-sample ingestion pricing (§9) scales with **cardinality**, which is what 200× multiplies hardest |
| Prometheus + Grafana on ECS with EBS | one task, restart on failure | cheapest | Prometheus's local TSDB is a single point of failure for exactly the signal you need during an incident |
| Prometheus + Thanos or Mimir on EKS | object-store-backed HA | cheapest at scale, fully controlled | a distributed monitoring system to monitor a platform of this size |

**Pick: AMP + AMG.** Scrape config becomes remote-write; everything the repo
actually owns — `docker/prometheus/rules/*.yml`, the runbook annotations, the
alert unit tests gated by `scripts/check-docs.sh` (c) and (c2) — is portable as
written. The one genuine caution is that at 200× it is cardinality, not sample
rate, that sets the bill.

**Repo change:** scrape config becomes remote-write. The rules and dashboards are
files that move unedited.

## 6. Iceberg cross-region: the absolute-path problem

The intuitive DR design — "turn on S3 Cross-Region Replication and the lake is
in two regions" — does not work, and the reason is specific enough to be worth
sourcing properly. All findings below were fetched **2026-08-29**.

### 6.1 Findings

| # | Finding | Confidence | Source |
|---|---|---|---|
| I1 | Every location field in Iceberg format versions 1–3 is a **fully-qualified** path: *"All location fields in format versions 3 and prior contain fully-qualified paths."* | confirmed by spec | [iceberg.apache.org/spec](https://iceberg.apache.org/spec/), *File Locations in Metadata* |
| I2 | The fields are table metadata `location` (*"Must be an absolute path when present"*), snapshot `manifest-list`, manifest-list entry `500 manifest_path`, manifest entry `100 file_path` (*"Full URI for the file with FS scheme"*), and position-delete `2147483546 file_path` | confirmed by spec | same |
| I3 | Relative paths arrive in **format v4 only**, and v4 *"is under active development and has not been formally adopted"* as of Iceberg 1.11.0 | confirmed by spec | same, *Format Versioning* + Appendix E; tracking [issue #13141](https://github.com/apache/iceberg/issues/13141) |
| I4 | `write.data.path` (*"Base location for data files"*) and `write.metadata.path` (*"Base location for metadata files"*) are **write-side only** — they change where new files go, never how recorded paths are resolved | confirmed by docs + spec Appendix F | [configuration](https://iceberg.apache.org/docs/latest/configuration/) |
| I5 | There is **no read-side path remapping** in Iceberg 1.x. Absolute paths are *"used as-is without modification"* | confirmed (spec design + absence of any such property) | spec |
| I6 | `rewrite_table_path` **exists**, added in Iceberg **1.8.0**: *"Stages a copy of the Iceberg table's metadata files where every absolute path source prefix is replaced by the specified target prefix."* It explicitly *"only stages rewritten metadata files and prepares a list of files to copy. The actual file copy is not included"*, returning a `file_list_location` CSV of source→target | confirmed by docs + release notes | [spark-procedures](https://iceberg.apache.org/docs/latest/spark-procedures/#rewrite_table_path), [releases](https://iceberg.apache.org/releases/) |
| I7 | `register_table` re-registers a `metadata.json` in a destination catalog, with the documented warning that *"Having the same metadata.json registered in more than one catalog can lead to missing updates, loss of data, and table corruption"* | confirmed by docs | [spark-procedures](https://iceberg.apache.org/docs/latest/spark-procedures/#register_table) |
| I8 | The **same bucket name in two regions is impossible**: *"General purpose buckets exist in a global namespace, which means that each bucket name must be unique across all AWS accounts in all the AWS Regions within a partition."* | confirmed by AWS docs | [bucket naming rules](https://docs.aws.amazon.com/AmazonS3/latest/userguide/bucketnamingrules.html) |
| I9 | Iceberg supports S3 **Access Points** as a *bucket → access-point mapping* (`s3.access-points.<bucket>=<arn>`), so metadata keeps its original `s3://` URIs and S3FileIO substitutes the access point at request time — *"useful for multi-region access, cross-region access, disaster recovery"*. Cross-region access points additionally need `use-arn-region-enabled=true` | confirmed by docs | [Iceberg AWS](https://iceberg.apache.org/docs/latest/aws/#s3-access-points) |
| I10 | Whether an `s3://<alias>.mrap/key` **path form** works in S3FileIO | **unverified** — no doc supports it; the documented mechanism is the bucket-mapping property in I9. Do not design on the path form | — |
| I11 | `s3.cross-region-access-enabled` (default `false`) lets S3FileIO reach the *same* bucket from another region. It does not change bucket names, so it does not help a CRR replica | confirmed by docs | [Iceberg AWS](https://iceberg.apache.org/docs/latest/aws/#s3-cross-region-access) |
| I12 | Latest Apache Iceberg release: **1.11.0, 2026-05-19** | confirmed | [releases](https://iceberg.apache.org/releases/) |
| I13 | Lakekeeper documents an `update-storage-profile` operation and the S3 profile's fields (`bucket`, `region`, `key-prefix`, `endpoint`, …), and freezes specific fields **for OneLake only** | confirmed | [Lakekeeper storage](https://docs.lakekeeper.io/docs/latest/storage/) |
| I14 | Whether Lakekeeper permits changing `bucket`/`region` on an **existing S3 warehouse** | **unverified** — the docs state the frozen fields for OneLake and say nothing equivalent for S3. Left out of the design as a claim; named as a thing to test | — |
| I15 | Lakekeeper cross-region replication / failover | **not documented anywhere found.** No claim made | — |

### 6.2 What this repository's own tables inherit

- Every table in [`docker/lake/ddl/lake.sql`](../../docker/lake/ddl/lake.sql) sets
  `'format-version' = '2'`, so **I1 applies to all of them**: every path in
  every `metadata.json`, manifest list, manifest and data-file entry is an
  absolute `s3://` URI. Relative paths are three format versions away (I3).
- The stack runs **Iceberg 1.8.1** (`tabulario/spark-iceberg:3.5.5_1.8.1`,
  pinned by digest in `docker/spark/Dockerfile`), which is `rewrite_table_path`'s
  first release (I6). **The mitigation is available in the image the repo
  already runs** — nothing needs upgrading to make the DR plan executable.
- The `rewrite_table_path` docs carry a limitation — *"Iceberg tables with
  partition statistics files are not currently supported"*. `grep` for partition
  statistics across `docker/lake/` returns nothing: no job computes them, so
  the limitation does not bite here.

### 6.3 Options considered for a readable cross-region replica

| Option | Mechanism | Verdict |
|---|---|---|
| CRR alone | replicate objects, point a catalog at them | **does not work.** The destination bucket has a different name (I8) and every metadata path names the source bucket (I1). The replica is byte-perfect and inert |
| Same bucket name in both regions | — | **impossible** (I8) |
| `write.metadata.path` / `write.data.path` | set them to the destination prefix | **does not solve it** (I4). New files go there; every existing path still names the source bucket. Useful for a *forward* migration, useless for failover |
| Wait for relative paths | format v4 | **not available** (I3). Correct long-term answer, no delivery date |
| **`rewrite_table_path` → copy → `register_table`** | stage rewritten metadata with the prefix swapped, copy per the emitted CSV, register in the destination catalog | **the recommended route.** Available at 1.8.1, officially documented, batch-shaped. Costs an RTO, not an RPO — see §8 |
| MRAP + `s3.access-points.<bucket>` | front both buckets, let S3FileIO route the original URIs regionally | **the only continuous option** (I9). No metadata rewrite. Inherits MRAP's own constraints, and MRAP availability was **not verified** — check before designing on it |

The two viable routes differ in *when the work happens*: `rewrite_table_path` is
a failover-time batch job that costs RTO; the access-point mapping is standing
configuration that costs nothing at failover. The batch route is recommended
first because it is fully documented, needs no unverified service, and its cost
is a number this design can state honestly.

`register_table`'s warning (I7) makes one operational rule non-negotiable:
**failover is a one-way move, not a fan-out.** The same `metadata.json` must not
be live in two catalogs. Failing back is a second `rewrite_table_path` in the
other direction, not a "switch the DNS back".

## 7. Multi-region DR design

### 7.1 Per-tier

| Tier | Mechanism | Notes |
|---|---|---|
| **Lake objects** | S3 Cross-Region Replication, data + metadata prefixes both | CRR is asynchronous and per-object; a snapshot's `metadata.json` can replicate before the manifests it references, so the replica is not point-in-time consistent. Failover must therefore pick a *snapshot* to recover to, not a wall-clock instant. `rewrite_table_path`'s `end_version` argument is exactly that control |
| **Catalog** | Lakekeeper in region B on RDS PostgreSQL with a cross-region read replica, promoted on failover | I14 is unverified, so the design does **not** assume the storage profile can be edited in place: the plan is `register_table` into a warehouse created for region B |
| **Bus** | MSK Replicator or MirrorMaker 2 to a second MSK cluster; or Redpanda Cloud's multi-region option | Redpanda Cloud's multi-region terms are **quote-based**, not on a public price page (§9) |
| **Capture** | re-place the tasks: capture is stateless between connections, so failover is "start the task in region B". A new `conn_id` and `conn_msg_seq = 1` mark the seam | the venue connection is to the public internet, so region choice is a latency question, not a reachability one |
| **Hot tier** | rebuild from the lake in region B. ADR-025 makes this the only supported reload path (`iceberg()`, glob banned) | the RTO is the rebuild duration, which nobody has measured at 200× |
| **Orchestration** | Prefect deployments defined as code (`docker/lake/flows/deploy_lake.py`); re-apply against a region-B API | trivially portable; it is configuration, not state |

### 7.2 What is deliberately not designed

An **active-active** two-region lake. Two regions committing to one Iceberg
table is a distributed-transaction problem the catalog does not solve, and
`register_table`'s own warning (I7) says the naive version corrupts tables. The
design here is **warm-standby storage, cold-standby compute**.

## 8. RPO / RTO reasoning

Every number in this section is a **design target**: chosen by this analysis
from the mechanism, not measured, because there is no deployment to measure.
The reasoning is given so a reader can disagree with the number by disagreeing
with the reason.

### 8.1 AZ loss, single-region multi-AZ deployment

| Tier | RPO | RTO | Reasoning |
|---|---|---|---|
| Capture | **~40 s** | ~40 s | the failover gap of §4.4: detection (~30 s on a 3 × 10 s health check) + task start and WS connect (**measured 3 s** on this host) + subscribe/resync. RPO = RTO here because the gap *is* the loss — public feeds do not replay |
| Bus | **0** | seconds | `replication.factor=3`, `min.insync.replicas=2`, rack-aware. An acknowledged write survives one AZ by definition; recovery is a leader election |
| Lake (S3) | **0** | 0 | S3 Standard is already multi-AZ within a region. Nothing to fail over |
| Catalog (RDS) | **0** | **1–2 min** | Multi-AZ is synchronous replication, so no committed transaction is lost; the RTO is AWS's failover, conventionally 60–120 s |
| Ingest | **0** | **≤ 5 min** | ADR-022: the in-flight run is a no-op with orphans (§3.1), and the next scheduled run resumes from the committed offsets. RTO is one cadence interval |
| Hot tier | **0** | **minutes to hours** | ADR-025 makes it derived and originating nothing, so RPO is 0 by construction. RTO is a reload from the lake, unmeasured at scale |
| Orchestration | **0** | ~1 min | RDS Multi-AZ behind it; flows are code |

**The AZ-loss story is strong everywhere except capture**, and capture's number
is a design decision (§4.5) rather than a limitation.

### 8.2 Region loss

| Tier | RPO | RTO | Reasoning |
|---|---|---|---|
| Capture | **minutes** | **~5 min** | the loss is everything between the regional event and the region-B task connecting: detection is now a human or a health check on a cross-region signal, which is minutes, not seconds |
| Bus | **seconds to minutes** | ~10 min | MirrorMaker 2 / MSK Replicator is asynchronous. The RPO is its replication lag, and the honest statement is "whatever the lag was", which is why the bus is a buffer and not the archive |
| Lake objects | **minutes** | — | S3 CRR is asynchronous. AWS publishes an S3 Replication Time Control SLA (15 min for 99.99 % of objects) — **not verified for this design**, and not assumed: the design target is stated as "the last fully-replicated snapshot", which is a snapshot id, not a clock |
| Lake readability | — | **hours** | this is the number that dominates. `rewrite_table_path` over every table, a copy per the emitted file list, `register_table` per table into the region-B catalog. It is a batch job proportional to *metadata* size, not data size — §6.1 I6 rewrites metadata only — but the file copy it prepares is proportional to data, unless CRR already moved it (it did), in which case the copy is a no-op and only the staged metadata is new |
| Catalog | **seconds** | **~15 min** | cross-region read replica promotion, plus the `register_table` pass above |
| Hot tier | **0** | **hours** | rebuild from the region-B lake, after the lake is readable. It is strictly downstream of the row above |

**Region-loss RTO is therefore hours, and dominated by one step**: making the
CRR'd Iceberg metadata point at the region-B bucket. That is the honest headline,
and it is a direct consequence of I1 — absolute paths — not of anything this
platform chose.

**The one design change that would collapse it** is the MRAP + access-point
mapping route (I9): with the original URIs routing regionally, there is no
metadata rewrite and the lake RTO falls to the catalog's. It is not recommended
first only because MRAP's current availability was not verified (I10).

```
       60 d Std-IA     816 GB x 0.0131  = $ 10.69
      275 d GIR      3,740 GB x 0.005   = $ 18.70
      PUTs ~912 k/mo x 0.0053/1,000     = $  4.83   -> ~$44/mo
200x:  30 d Standard  82,200 GB x 0.024 = $1,972.80
       60 d Std-IA   164,400 GB x 0.0131= $2,153.64
      275 d GIR     753,500 GB x 0.005  = $3,767.50
      PUTs ~1.2 M/mo                    = $    6.36  -> ~$7,900/mo
```

GET charges are query-driven and **not modelled** — there is no query workload to
model. **The lifecycle is a 3× lever**: the same 1,000,100 GB left entirely in S3
Standard would be `1,000,100 × 0.024` = **$24,002/mo** against $7,894. Year 2 is where
Deep Archive earns its keep: the same 1,000,100 GB at
$0.0018 is $1,800/mo instead of $5,000/mo in GIR, which is the trade chapter 17
§5 says belongs in an ADR when it is taken.

**Catalog.** 1×: 2 Lakekeeper tasks at 0.5 vCPU / 1 GB = $41; RDS
`db.t4g.medium` Multi-AZ $106 + 100 GB gp3 Multi-AZ $27 = $133. **$174/mo**.
200×: 4 tasks at 1 vCPU / 2 GB = $166; `db.m7g.large` Multi-AZ $285 + 200 GB $53.
**$504/mo**.

**Ingest (EMR Serverless).** 1×: 288 runs/day at 4 vCPU / 16 GB for 60 s (EMR
Serverless bills a 1-minute minimum; the measured runs on this host were 17–92 s
for 0.08–2.7 M rows, `spark_conf.py`): `0.01667 × (4 × 0.060528 + 16 ×
0.006643)` = $0.0058/run × 8,761 = $51; nightly maintenance 8 vCPU / 32 GB for
20 min = $7. **$58/mo**. 200×: 32 vCPU / 128 GB for 4 min = $0.186/run × 8,761 =
$1,629; maintenance 128 vCPU / 512 GB for 2 h = $678. **$2,307/mo**.

**Hot tier.** ClickHouse Cloud is **quote-based** and gets no number. Self-managed
1×: 2 × `r7i.2xlarge` replicas = $908 + 2 × 200 GB gp3 = $37. **$945/mo**. 200×:
4 × `r7i.2xlarge` = $1,815 + 4 × 2,000 GB = $742. **$2,557/mo**. **The 3-node
Keeper ensemble is not priced** — no rate for a suitable small instance class was
verified, so it is named and left out rather than guessed. It is a real cost and
the totals understate by it.

**Orchestration.** Self-hosted: 2 server tasks at 1 vCPU / 2 GB + 2 workers at
0.5 / 1 = $124; RDS `db.t4g.medium` Multi-AZ + 50 GB = $119. **$244/mo, flat at
both scales** — it is a control plane, not a data path. Prefect Cloud Starter at
$100/mo is cheaper and §5.8 explains why it is not the pick yet.

**Observability.** 1×: ~20,000 active series at 15 s ≈ 3,504 M samples/mo.
`40 M free + 1,960 M @ $0.90/10 M + 1,504 M @ $0.35/10 M` = $229; storage under
the 10 GB free tier; query ~$1. AMG 1 editor + 2 viewers = $19. **$249/mo**.
200×: ~150,000 series ≈ 26,280 M samples/mo = $1,026 + $1 storage + $10 query +
$19 AMG. **$1,056/mo**. Cardinality is a **design target and the shakiest input
here**: it depends on whether metrics stay per-venue or become per-symbol, and
per-symbol at 10,000 instruments would be a different order of magnitude.

**Cross-AZ transfer.** Produce + consume only (item 5 of §9.2's unverified list),
two-thirds assumed to cross an AZ, $0.01/GB per direction. 1×:
`35.66 × 2 × 0.667 × 0.01 × 30.42` = **$14/mo**. 200×:
`7,132 × 2 × 0.667 × 0.01 × 30.42` = **$2,894/mo**.

### 9.5 What the totals say

| Tier | 1× / month | 200× / month |
|---|---|---|
| Capture — Fargate | $31 | $829 |
| Bus — MSK provisioned | $528 | $7,031 |
| Schema registry — Glue | $0 | $0 |
| Lake — S3 (end of year 1, lifecycled) | $44 | $7,900 |
| Catalog — Lakekeeper ECS + RDS Multi-AZ | $174 | $504 |
| Ingest — EMR Serverless | $58 | $2,307 |
| Hot tier — 2/4 ClickHouse replicas on EC2 | $945 | $2,557 |
| Orchestration — Prefect self-hosted | $244 | $244 |
| Observability — AMP + AMG | $249 | $1,056 |
| Cross-AZ data transfer | $14 | $2,894 |
| **Total** | **~$2,287** | **~$25,322** |

**Estimate, list price, not measured.** Excludes the ClickHouse Keeper ensemble
(unpriced), GET requests (no query workload modelled), NAT gateways, load
balancers, backups, support plans and any reserved or savings-plan discount.

Two things fall out that the per-tier tables do not show:

1. **HA has a floor, and at 1× the floor is most of the bill.** The hot tier,
   orchestration and catalog — $1,363 of $2,287, **60 %** — are almost entirely
   *redundancy*, not capacity. They cost the same whether the platform ingests
   13.6 GB/day or nothing. That is the real price of the word "highly available",
   and it is the argument for measuring the ClickHouse rebuild before buying
   replicas (§5.7): if the rebuild is fast enough, the largest single line at 1×
   is optional.
2. **At 200× the shape inverts entirely.** Storage, bus and *data transfer* are
   $17,825 of $25,322, **70 %** — and cross-AZ transfer, a line that does not
   exist on one host and appears in no capacity model built on GB/day, is larger
   than the entire 1× bill. It is billed per GB in each direction and scales with
   topology rather than with stored bytes, which is why no capacity model built on
   GB/day would ever have surfaced it.

The ratio is worth stating: **200× the data costs ~11× the money.** Storage
lifecycle and serverless billing are why, and both are design choices this
platform already made.
