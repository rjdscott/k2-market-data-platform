# Storage credentials: one root key held by every engine, and what replaces it

**Date:** 2026-11-26
**Question:** every engine reaches the lake with MinIO's root credential, which was MinIO's own
default pair and was reachable from the local network. What least-privilege credentials does
this stack support with the releases it pins, in what order can a running stack move to them,
and what does that still leave open?
**Status:** design, not a decision. Section 9 lists what an ADR has to decide. Nothing here
has been applied to the running stack.

The trigger is the P3 audit of 2026-11-26 and the containment that followed it (every published
port on `127.0.0.1`, [SECURITY.md](../../SECURITY.md)). Containment closed the network path. It
did not change who holds the key, and the key has to be treated as compromised: MinIO printed its
`Detected default credentials` warning at each start, which it prints only for its built-in
default pair, its API and console listened on every interface, and Trino's log printed the
access key.

Every claim below says where it comes from: **probed** (a throwaway container of the pinned
image, no network to the stack, canary credentials), **read** (a read-only GET or a listing on
the live stack, no secret printed), or **docs** (the vendor's documentation, cited). Steps
nobody has run say so.

---

## 1. Who holds the credential today

Read on 2026-11-26 from `docker-compose.yml`, the code, and the live stack.

| Holder | How it gets the key | What it does with it |
|---|---|---|
| `minio` | `MINIO_ROOT_USER` / `MINIO_ROOT_PASSWORD` | is the root identity |
| `lake-init` | same two variables | `mc mb` the bucket; creates each Lakekeeper warehouse with the pair as its storage credential (`docker/lake/init-lake.sh`) |
| Lakekeeper, per warehouse | the pair stored in its database at warehouse creation, encrypted with `LAKEKEEPER_ENCRYPTION_KEY` | validation, its own reads and writes, purge on drop, and **remote signing for Spark** (below) |
| `spark-iceberg`, `lake-ddl`, every Airflow task that `docker exec`s into Spark | `AWS_*` and `MINIO_ROOT_*` in the container environment | `spark_conf.py` hands them to the `lake` catalog's S3FileIO; `maintenance.py` builds a second S3FileIO with them to list prefixes for orphan removal |
| `trino`, six catalogs | `${ENV:MINIO_ROOT_USER}` / `${ENV:MINIO_ROOT_PASSWORD}` in every catalog file, generated by k2gen for the five domain catalogs | reads `lake` (warehouse `k2`), reads and writes each domain warehouse |
| notebooks, `scripts/parity_*.py`, `scripts/replay_export.py` | read from `.env` on the host | DuckDB S3 secret, `ACCESS_DELEGATION_MODE 'none'`, warehouse `k2` only |
| `make screenshots` | passed into the container by name | MinIO console login at `:9001` |
| runbooks: ClickHouse rebuild, lake recovery, disk usage; `scripts/chaos/lake-minio-stop.sh` | typed or read from `.env` by the maintainer | ClickHouse `iceberg()` reads; `mc` listings and admin |
| `lake-metrics` | none | reads Lakekeeper's REST API and `statvfs` on the volume only |

**Spark's table IO is signed by Lakekeeper, with Lakekeeper's stored copy of the root key, not
with Spark's own.** Read: `GET /catalog/v1/<prefix>/namespaces/gold/tables/trades` with no
delegation header returns `s3.remote-signing-enabled: true` and a signer endpoint, and every
warehouse's profile has `remote-signing-enabled: true` (never set by `init-lake.sh`, so the
default). Lakekeeper's docs: with no `X-Iceberg-Access-Delegation` header "Lakekeeper vends
credentials if the profile enables it", and "falls back to remote signing otherwise"
([Storage](https://docs.lakekeeper.io/docs/latest/storage/)); `sts-enabled` is false here.
Lakekeeper's audit log held 19,644 `read_data` and 58 `write_data` authorizations on warehouse
`k2` in three minutes of a `lake_ingest` run (2026-11-25 23:22 to 23:25 UTC), and 84,049 lines
mentioning `/sign` in the hour to about 23:30 UTC. During the 23:10 `dbt_marts` run (11 tables created,
11 dropped, 30 commits in the domain warehouses) there was no `read_data` or `write_data` on
any domain warehouse: **Trino does not use remote signing and reads and writes with its static
key**.

Two consequences shape the design. Scoping Spark's static key changes nothing while signing is
on. And the signer answers anyone who reaches Lakekeeper, which is unauthenticated
(`authz-backend` `allow-all`, every actor `anonymous` in its audit log): any process on the host,
through `127.0.0.1:18181`, and any container on `k2-net` can have an S3 request signed for any
table. Lakekeeper's docs add that MinIO "do[es] not" check every part of a signed request, so a
signed request can be altered, for example "to delete files outside its own" table, and advise
vended credentials instead.

## 3. The design

The root pair is used by MinIO and by `lake-init` only, plus the maintainer's admin runbooks.
Every other consumer gets its own MinIO user, whose policy names the prefixes it needs and
nothing else. Remote signing goes off on every warehouse, so each engine's own key is the one
that reaches MinIO.

Warehouse locations are `s3://k2-lake/warehouse/<warehouse>/<table uuid>/...`, one prefix per
warehouse (read: Lakekeeper's `key-prefix` per warehouse and the volume listing). Today only
`k2`, `market_analytics` and `governance` hold objects.

| Consumer | MinIO user | Policy | Why that much |
|---|---|---|---|
| MinIO, `lake-init` | root | all | `lake-init` makes the bucket, the users and policies, and sets each warehouse's credential |
| Lakekeeper (every warehouse's stored credential) | `k2-lakekeeper` | `k2-lake-write` on `warehouse/*` | validation writes, reads, deletes and lists a probe prefix in each warehouse; its own metadata reads and writes; the purge after a drop, which `dbt_marts` causes hourly in the domain warehouses |
| Spark: `spark-iceberg`, `lake-ddl`, the Airflow tasks | `k2-spark` | `k2-lake-write` on `warehouse/k2/*` | ingest, compaction, expiry and orphan removal on the lake; no domain warehouse (`maintenance.py` and `spark_conf.py` address `k2` only) |
| Trino catalog `lake` | `k2-trino-lake` | `k2-lake-read` on `warehouse/k2/*` | ADR-044's read-only promise, enforced by storage as well as the connector |
| Trino domain catalogs, stage 1 | `k2-trino-marts` | `k2-lake-write` on each domain prefix, from `warehouses.txt` | builds, `expire_snapshots` and `remove_orphan_files` (`dbt/macros/expire_mart_snapshots.sql`); nothing on `k2`, which domain models read through catalog `lake` |
| Trino domain catalogs, stage 2 | `k2-trino-<domain>` | `k2-lake-write` on its own prefix | only after Trino authenticates its users (section 6) |
| notebooks, parity, replay export, the ClickHouse rebuild runbook, `make screenshots` | `k2-reader` | `k2-lake-read` on `warehouse/k2/*`, plus listing `""` and `warehouse/` for the console's browser | reads only; DuckDB reaches no domain warehouse |
| `lake-metrics` | none | none | unchanged |

The two policies, with `PREFIXES` the list from the table. The read policy:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {"Effect": "Allow", "Action": ["s3:GetBucketLocation"], "Resource": ["arn:aws:s3:::k2-lake"]},
    {"Effect": "Allow", "Action": ["s3:ListBucket"], "Resource": ["arn:aws:s3:::k2-lake"],
     "Condition": {"StringLike": {"s3:prefix": ["warehouse/k2/*"]}}},
    {"Effect": "Allow", "Action": ["s3:GetObject"], "Resource": ["arn:aws:s3:::k2-lake/warehouse/k2/*"]}
  ]
}
```

The write policy, here for `market_analytics`; Lakekeeper's names `warehouse/*`, Spark's
`warehouse/k2/*`, stage 1's Trino one lists every domain prefix:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {"Effect": "Allow", "Action": ["s3:GetBucketLocation", "s3:ListBucketMultipartUploads"],
     "Resource": ["arn:aws:s3:::k2-lake"]},
    {"Effect": "Allow", "Action": ["s3:ListBucket"], "Resource": ["arn:aws:s3:::k2-lake"],
     "Condition": {"StringLike": {"s3:prefix": ["warehouse/market_analytics/*"]}}},
    {"Effect": "Allow",
     "Action": ["s3:GetObject", "s3:PutObject", "s3:DeleteObject",
                "s3:AbortMultipartUpload", "s3:ListMultipartUploadParts"],
     "Resource": ["arn:aws:s3:::k2-lake/warehouse/market_analytics/*"]}
  ]
}
```

Both are the probed shapes. `k2-reader`'s console listing (`""`, `warehouse/`) is not probed.

**Keys are pre-generated in `.env`, and `lake-init` converges MinIO and Lakekeeper to them.**
Access keys are fixed names in `docker-compose.yml` (not secrets); each secret is one `.env`
line, `openssl rand -hex 24`: `K2_S3_LAKEKEEPER_SECRET`, `K2_S3_SPARK_SECRET`,
`K2_S3_TRINO_LAKE_SECRET`, `K2_S3_TRINO_MARTS_SECRET`, `K2_S3_READER_SECRET`. The suffix is
one `scripts/check-env.py` already refuses as a placeholder. On every run `lake-init` creates or
replaces the policies and users (both idempotent, probed), creates new warehouses with
`remote-signing-enabled: false`, and posts each warehouse's credential to `k2-lakekeeper`.
Rotation is then an edit of `.env` and `docker compose up -d lake-init`, plus a recreate of the
consumer. The alternative, an init job that generates keys and writes them to a file, does not
fit compose: `environment:` and `env_file:` are read at `up`, before any init container runs.
The fresh clone stays one path, `cp .env.example .env`, fill, `make up`; five more values to
fill argue for a `make env` that writes every placeholder with `openssl rand`, not built here.

**What changes in code** (none of it written yet): Spark's and `lake-ddl`'s environment lose
`MINIO_ROOT_*` and carry `AWS_ACCESS_KEY_ID=k2-spark` and its secret, which `spark_conf.py` and
`maintenance.py` read; Trino loses `MINIO_ROOT_*` and gets its two secrets; `lake.properties`
and k2gen's `_CATALOG_REST` template name them; `init-lake.sh` grows the user, policy and
credential steps; `notebooks/k2lake.py`, the parity and replay scripts, the screenshots tool and
the ClickHouse rebuild runbook switch to `k2-reader`; `make test-trino` starts with the new
variable names.

**Stage 2, per-domain Trino keys.** k2gen would write `s3.aws-access-key=k2-trino-<domain>` and
`s3.aws-secret-key=${ENV:K2_S3_TRINO_<DOMAIN>_SECRET}` into each catalog (domain id upper-cased,
`-` to `_`), and a users file beside `warehouses.txt` for `lake-init`. Compose is not
generated, so the `trino` service's `environment:` would list each variable by hand, and a
`make test-k2gen` check would fail until it names every generated one, the pattern
`contracts/` already uses for partitioning.

## 4. Migration on the running stack

After the rehearsal (section 5) passes and the code above is merged. Every step is **NOT YET
RUN**. Pausing first keeps every restart out of a write: `lake_ingest`, `lake_maintenance` and
`dbt_marts` paused, then `airflow dags list-runs <dag> --state running` empty for all three.
Redpanda keeps raw records for 48 h or 2 GiB a partition, whichever binds first, so a 30 to 45
minute pause costs lag, not data.

| # | Step | What breaks, for how long | Verify | Roll back |
|---|---|---|---|---|
| M1 | Read-only inventory as root: `mc admin user ls`, `mc admin user svcacct ls`, `mc admin policy ls`, `mc anonymous get k2/k2-lake`, `mc ilm rule ls`, `mc event ls`, `mc ls k2` | nothing | anything not in section 7's list stops the migration: a root holder can leave a user, a key or an anonymous policy that rotating root does not remove | none needed |
| M2 | Audit on: the MinIO environment of section 8, its topic created first, recreate `minio` | S3 down while MinIO restarts, about 15 s (healthcheck interval) | records arrive on the topic | drop the variables, recreate |
| M3 | `docker compose up -d lake-init` on the new code: users and policies | nothing: additive | `mc admin user ls` lists the five users | `mc admin user remove`, `mc admin policy remove` |
| M4 | each warehouse's credential to `k2-lakekeeper` (the `lake-init` step, or `POST .../storage-credential` with the full body) | nothing if the policy is right: Lakekeeper validates before saving, and refuses a key that cannot write, read and delete | `GET` shows `access-key`; one manual `lake_ingest` run commits; no failed signing in Lakekeeper's log | post the root pair back, still valid until M7. The body must carry a credential: an empty one removes it |
| M5 | recreate `spark-iceberg` and `trino` with the new environment | Trino about a minute; Spark nothing while paused | `dbt_marts` once: builds and tests; Trino reads `lake` | revert the commit, recreate |
| M6 | `remote-signing-enabled: false` on every warehouse (`POST .../storage`, the same bucket and prefix, with the credential) | none if `k2-spark` is right; otherwise every Spark read and write fails until rolled back | the table config no longer carries a signer; `lake_ingest` and `lake_maintenance` succeed; Lakekeeper logs no `read_data` or `write_data` | the same call with `true` |
| M7 | rotate root, user and password, in `.env`; recreate `minio` | S3 down about 15 s; anything still on root fails, which by now is only `lake-init` and the admin runbooks | the old pair refused, the new accepted, every user still works (all probed) | the old pair back in `.env`, recreate. It is compromised: only to restore service |
| M8 | unpause; `make health`; `python3 scripts/check-env.py` passes, so `make up` works again | nothing | the interim state in `docs/development/setup.md` ends here | none |

## 5. Rehearsal, before anything live changes

A throwaway compose project of its own, because `docker-compose.yml` fixes every
`container_name` and a second project from it would collide with the live one: the pinned
MinIO, `postgres:15-alpine`, Lakekeeper 0.13.9 with its migrate step, `lake-init` from the
branch, the built `k2-spark-iceberg` image and `trinodb/trino:484` with the real `etc/`, all on
an `--internal` network with no published port. Each line passes, or nothing on the live stack
changes:

1. The policies: `k2-trino-lake` and `k2-reader` cannot put or delete under `warehouse/k2/`;
   `k2-trino-marts` cannot touch `warehouse/k2/`; `k2-spark` cannot touch a domain prefix.
2. Lakekeeper refuses, on `storage-credential`, a key without delete, and the stored credential
   still works; then accepts `k2-lakekeeper`.
3. Signing off: the table config has no signer; Spark ingests, compacts, expires and removes
   orphans with `k2-spark`, and Lakekeeper's log shows no `read_data` or `write_data`.
4. Trino: `dbt build` and `expire_mart_snapshots` pass on a domain catalog; a domain catalog
   pointed at `k2` with the marts key gets `Access Denied` from MinIO.
5. A dropped domain table's files are gone after Lakekeeper's purge, with `k2-lakekeeper`.
6. Root rotated mid-rehearsal: lines 3 to 5 still pass.
7. Audit: each consumer's records carry its own access key.
8. A fresh `up` on empty volumes converges to the same state, and `make test-trino` passes.
9. Each rollback in section 4 restores the state before its step.

## 6. Why not vended credentials or remote signing

Both put Lakekeeper between the engines and MinIO, which is where per-table scoping belongs in
the end. Neither works here yet. Remote signing is on today and protects nothing: MinIO does
not check the whole signed request, and the signer serves any caller. Vended credentials need
MinIO's STS, which Lakekeeper does not test, and would hand table-scoped read-write keys to any
caller as long as Lakekeeper authorizes everyone. Both become worth it with authentication on
Lakekeeper, which is the entitlements phase (P5, ADR-031); so do per-domain Trino keys, which
until Trino authenticates its users stop a misconfigured catalog, not a person who claims
`dbt_<domain>` in a header.

## 7. Evidence of use from outside, and what cannot be known

Read on 2026-11-26, without the credential:

- **No audit trail exists.** `k2-minio` has no `MINIO_AUDIT_*` variable (names listed, values
  not), nothing in the repository configures audit, and Prometheus does not scrape MinIO.
  `mc admin trace` shows live traffic only. `docker logs k2-minio` holds 20 lines: two startup
  banners and the default-credentials warning twice, which quotes the pair. MinIO's own request
  counters reset at its last start (2026-11-25 22:39 UTC) and reading them needs the
  credential; not read.
- **No IAM identity was added.** The volume, through `lake-metrics`' read-only mount, has no
  `.minio.sys/config/iam/users`, `service-accounts`, `policies` or `groups`. It has one STS
  identity, written 2026-11-25 20:34:44 UTC, six minutes before the screenshots commit of
  #210 (20:40 UTC), whose console login issues one; consistent with it, not proof.
- **One bucket the code does not make:** `scratch-p4-landing`, created 2026-11-25 21:36 UTC,
  holding four objects under `landing/fx-reference/ecb_fx_daily`. That reads like P4 work on
  the FX domain; the owner has to confirm it.
- **Not knowable now:** whether anyone used the default pair from the network before
  2026-11-26. Requests signed with a valid key look like the stack's own, nothing recorded
  source addresses, and an intruder with root could have changed objects. The checks that
  remain are partial: snapshot histories against the schedules, objects not referenced by
  any table, and the M1 inventory.

## 8. Audit logging from here on

On, through MinIO's Kafka target to a Redpanda topic, so it needs no new service:

```yaml
# minio environment
MINIO_AUDIT_KAFKA_ENABLE_k2: "on"
MINIO_AUDIT_KAFKA_BROKERS_k2: redpanda:9092
MINIO_AUDIT_KAFKA_TOPIC_k2: k2.audit.minio
MINIO_AUDIT_KAFKA_QUEUE_DIR_k2: /data/.audit-queue   # buffers while Redpanda is down
```

with the topic made by `redpanda-init`, one partition, `retention.bytes` capped. Probed as
written, against the pinned images. **Estimate, not measured:** Spark alone made about 84,000
S3 requests an hour (the signing lines above), so at 1,687 bytes a record the topic grows
about 140 MB an hour, 3.4 GB a day; a 2 GiB cap keeps roughly 14 hours. Measure the real rate
for a day after M2 and fix the cap in the ADR of section 10, since it lands on the disk
`LakeDiskUsageHigh` watches.

## 9. What stays open after this design

None of this makes the stack secure, and each limit below is a stated non-goal
([ADR-028](../adr/ADR-028-non-goals-and-honest-limits.md) section 8):

- Trino's identity is the unauthenticated `X-Trino-User` header
  ([ADR-044](../adr/ADR-044-producer-lake-and-domain-mart-warehouses.md)).
- Lakekeeper is `allow-all`: anyone on the host or on `k2-net` can drop any table through its
  REST API, and Lakekeeper then purges the files with its own key. Scoped engine keys do not
  stop that.
- No TLS anywhere; secrets in plain text in `.env` and in container environments, readable by
  anyone with the Docker socket, which the Airflow scheduler holds.
- Loopback keeps other machines out, not other users of the host.

## 10. Decisions for an ADR

1. The root pair is for MinIO and `lake-init` only; no engine holds it. This replaces
   ADR-044's "today Trino holds the root keys" and moves "Trino's own storage key" forward from
   the entitlements phase.
2. One MinIO user per consumer, prefix-scoped, the five of section 3. Per-domain Trino keys
   wait for authenticated Trino identity.
3. Remote signing off on every warehouse, `init-lake.sh` creating new ones that way; vended
   credentials wait for Lakekeeper authentication and an STS it tests.
4. Secrets pre-generated in `.env`, converged by `lake-init` on every `up`.
5. The root pair is rotated in the migration and treated as compromised.
6. MinIO audit to `k2.audit.minio`, with a byte cap measured before it is fixed.

## Open questions

- Does Spark, with signing off, use `k2-spark` on every path: data, manifests, deletes and
  `maintenance.py`'s listing? Rehearsal line 3.
- The validation behaviour is from Lakekeeper's latest docs, not 0.13.9's: rehearsal line 2.
- On Docker Desktop, the remote address MinIO records for a request through a published port
  may be the engine's forwarder, not the client. If so the audit names keys, not machines.
- Does the console browser need more than listing `""` and `warehouse/` for `k2-reader`?
- `scratch-p4-landing` and the STS identity: the owner confirms both before M1 can pass.
