# ADR-054: Each engine gets its own storage key, and root leaves the engines

**Status:** Proposed. **Not ready to accept**: section 9 lists what must be proven on the rehearsal
stack first, and nothing in this ADR's acceptance depends on how those results turn out; if one
fails, the design changes and is reviewed again.
**Date:** 2026-11-26
**Author:** Platform
**Category:** Security / Storage
**Decided by:** the owner on 2026-11-26, in outline (security fixes before phase P4; the root
credential treated as compromised; an independent review before acceptance). Split from the first
draft of [ADR-052](ADR-052-backup-and-restore-of-irreplaceable-tables.md) by the review of
2026-11-26, whose findings B2, S3, S4 and S5 this answers.
**Evidence:** [research note](../research/2026-11-26-storage-credentials-least-privilege.md)
("note §n"), which probed MinIO's user policies on the pinned image.

---

## In plain words

Every engine that touches the lake, and the catalog itself, uses MinIO's master key, which was the
factory default and was reachable from the local network, so it has to be treated as known. We will
give each engine its own key that can do only its job, stop the catalog from signing other engines'
storage requests with its own copy, forbid the catalog's key to delete or overwrite the
irreplaceable tables' files at prefixes pinned on the host, and only then change the master key.
It costs six secrets in `.env`, generated by `make env`, and about three minutes of restarts in
two paused windows. It is not ready to accept: the behaviours it relies on must first be shown on a
throwaway stack. The owner needs to decide nothing new, beyond accepting it once they are.

---

## Context

Terms are explained where they first appear; the [glossary](glossary.md) has each one too.

### Who holds the master key

MinIO's **root credential** is the one identity that can do everything: read, write and delete any
object, erase old versions, and change bucket settings, users and policies. A MinIO **user** is a
second access key and secret that root creates, and its **policy** lists the S3 actions it may take
on named bucket paths; everything else is refused ([glossary](glossary.md#minio-users-policies-and-the-root-credential)).
Today there are no users, and root is in the environment of `minio`, `lake-init` (the one-shot that
creates the bucket and the warehouses), `spark-iceberg`, `lake-ddl` and `trino` (all six catalogs),
and in every Lakekeeper warehouse's stored **storage credential**, the key Lakekeeper uses to write
each table's `metadata.json`, validate the warehouse and purge a dropped table (`docker inspect`,
compared in-process; note §1). Root's user equals its password, MinIO's factory pair.

### Remote signing

With **remote signing** on, an engine asks Lakekeeper to sign each of its S3 requests with that
stored key instead of using its own ([glossary](glossary.md#storage-credential-and-remote-signing)).
Every warehouse has it on (`remote-signing-enabled: True`), and `raw.messages`' table config names
the signer: `POST /catalog/v1/signer/<warehouse id>/tabular-id/<table id>/v1/aws/s3/sign`. Lakekeeper
signs for any caller, and MinIO does not check every part of a signed request (note §1). While it is
on, Spark's own key is never used, so scoping it changes nothing.

### What a scoped key does not stop by itself

- **Pointer moves.** The catalog is unauthenticated, and a rollback or a forged position deletes
  nothing; [ADR-053](ADR-053-recoverable-deletes-and-guards.md) puts those checks in the jobs.
- **Overwrites.** A refusal of deletes leaves `PutObject` over an existing name: with
  [ADR-053](ADR-053-recoverable-deletes-and-guards.md)'s versioning the original survives only as a
  noncurrent version, which the lifecycle rule erases after the window.
- **Keys a key can mint.** A MinIO user can create access keys of its own ("service accounts") and,
  through MinIO's security token service, temporary credentials; both can outlive a change of the
  user's secret (the review's S3; not probed).
- **Files beside the keys.** `lake-metrics` mounts the whole MinIO data volume read-only, for one
  `os.statvfs` call (`_refresh_disk` in `docker/lake/metrics.py`), and that volume holds MinIO's
  identity store: `.minio.sys/config/iam/sts` exists there (`ls`, read-only, 2026-11-26).
- **One Trino process loads every catalog file**, and its identity is the unchecked
  `X-Trino-User` header ([ADR-044](ADR-044-producer-lake-and-domain-mart-warehouses.md)), so keys per
  domain would all sit in one process that any user can steer.

## Decision

**We will give each engine a MinIO user whose policy allows only its job, turn remote signing off
so each engine's own key is the one that reaches MinIO, forbid the catalog's key to delete or
overwrite the irreplaceable tables' files at prefixes read from the host's pins and refuse to start
on a mismatch, and rotate the root credential last, because root is compromised and the storage
layer is the one place a refusal holds whatever the unauthenticated catalog or Trino are told.**
Scope: this single host; per-domain keys wait for Trino authentication in P5.

### 1. The keys

| Identity | Held by | Read | Write | Delete |
|---|---|---|---|---|
| root | `minio`, `lake-init`; the owner's admin runbooks | everything | everything | everything; **the only key that can erase a version** |
| `k2-lakekeeper` | every warehouse's storage credential | `warehouse/*` | `warehouse/*` **except the irreplaceable tables' `data/`** | `warehouse/*` **except the irreplaceable tables' prefixes** |
| `k2-spark` | `spark-iceberg`, `lake-ddl`: ingest, decode, DDL, rebuild | `warehouse/k2/*` | `warehouse/k2/*` | nothing |
| `k2-maintenance` | the Airflow scheduler's environment, passed into `spark-iceberg` for the nightly run only | `warehouse/k2/*` | `warehouse/k2/*` | `warehouse/k2/*` |
| `k2-trino-lake` | `trino`, catalog `lake` | `warehouse/k2/*` | nothing | nothing |
| `k2-trino-marts` | `trino`, the five domain catalogs | the domain prefixes in `docker/lake/generated/warehouses.txt` | same | same |
| `k2-reader` | notebooks, parity and replay scripts, the ClickHouse rebuild runbook, `make screenshots` | `warehouse/k2/*` | nothing | nothing |
| `k2-backup` | ADR-052's host job | `warehouse/*` | `k2-ops/backup/*` | nothing |

"Delete" is a plain `DeleteObject`, which under ADR-053's versioning leaves a delete marker.
Every policy but root's also carries an explicit `Deny` of `s3:DeleteObjectVersion`, the bucket
settings (`s3:PutBucketVersioning`, `s3:PutLifecycleConfiguration`, `s3:PutBucketPolicy`,
`s3:DeleteBucketPolicy`, `s3:PutBucketObjectLockConfiguration`), `admin:*` and `sts:*`: listing
what is refused, not only what is allowed, so a policy edit cannot widen them by accident.

**Why the ingest key deletes nothing.** Compaction writes new files and commits a snapshot that no
longer lists the old ones; files are deleted only by snapshot expiry and orphan removal, in the
nightly `docker/lake/maintenance.py`. The ingest's only deletes are clean-ups after a failed write,
and a refused clean-up leaves orphans that maintenance removes. The maintenance key reaches the
Spark container only for its run, through `docker exec --env K2_S3_MAINTENANCE_SECRET` (the name
alone, so the value comes from the scheduler's environment and appears in no command line or task
log). The scheduler already holds the Docker socket, so carrying it adds nothing there; a process
that persists in the Spark container through the nightly run can still read it, and ADR-053's
versioning and guards are what bound that.

### 2. The pinned refusal

`k2-lakekeeper`'s policy carries a `Deny` of `s3:DeleteObject` on each irreplaceable table's
`warehouse/<warehouse>/<UUID>/*` and of `s3:PutObject` on its `.../data/*` (Lakekeeper must still
write `metadata/`). The prefixes come from ADR-053's **pins**, an append-only host file of each
irreplaceable table's UUID and location ([glossary](glossary.md#pinned-table-identity)), never from
the catalog: `lake-init` compares the two and fails closed on any difference. Deriving them from the
catalog on every `up` would let a rename move the protection: rename `raw.messages`, run `up`,
`lake-ddl` creates an empty table of the same name, the refusal follows the new UUID, and a forced
drop of the renamed table purges the real files (the review's B2). With the pins, that `up` stops at
`lake-init`.

The same overwrite is still open to `k2-spark` and `k2-maintenance`, which must write raw's data
files: there the original is a noncurrent version for ADR-053's window, and ADR-052's copy keeps it
indefinitely.

### 3. Remote signing off

Each warehouse's storage profile gets `remote-signing-enabled: false` through
`POST /management/v1/warehouse/{id}/storage`, the call that changes a profile; it must carry the
credential, because "the existing credential is not re-used" (Lakekeeper 0.13.9's management
OpenAPI, `UpdateWarehouseStorageRequest`), and it keeps ADR-053's `push-s3-delete-disabled: false`.
With signing and STS (temporary keys Lakekeeper would hand out; `sts-enabled` is false here) both
off, the table config names no signer and Iceberg's S3 client uses the key Spark configures, as
Trino already does: the research note found no Lakekeeper data authorization on any domain
warehouse during a dbt run (note §1).

### 4. Trino, and what one key for all domains buys

Two keys: `lake` reads `warehouse/k2` and can write nothing, so ADR-044's read-only `lake` holds at
storage as well as at the connector; and one key for the five domain catalogs. Exactly what that
shared key buys: no Trino catalog can write the producer lake, whatever a catalog file or a table
location says; a leak of it exposes only marts, which are rebuilt from the lake, and the domains'
results tables, which ADR-052 copies; and Trino no longer holds a key that can erase versions or
change the bucket. What it does not buy: separation between domains, since any Trino user who
claims a writer's name in the header can reach any domain catalog. A key per domain would separate
nothing more until Trino authenticates its users (P5). k2gen, the contract tool that generates the
catalogs, would then write `s3.aws-access-key=k2-trino-<domain>` and
`${ENV:K2_S3_TRINO_<DOMAIN>_SECRET}` per catalog and a users file beside `warehouses.txt` for
`lake-init`, and `make test-k2gen` would fail until the `trino` service's environment and
`.env.example` name each generated variable.

### 5. How keys are made, rotated and kept single

Access keys are fixed names in `docker-compose.yml`; each secret is one `.env` line,
`K2_S3_<NAME>_SECRET`, written with every other placeholder by `make env` (which refuses to overwrite
an existing `.env`; `make up` runs it when `.env` is missing, so a fresh clone is still `make up`).
On every `up`, `lake-init` converges MinIO and Lakekeeper to `.env`, and asserts that no user has an
access key beyond its own (`mc admin user svcacct ls`), failing closed otherwise. Rotation removes
the user and creates it again (`mc admin user remove`, then `add`), not a change of its secret,
because removing the parent is what invalidates the access keys and temporary credentials it may
have minted; then the warehouse credentials are posted again and the holder recreated.

### 6. `lake-metrics` stops mounting MinIO's volume

It mounts an empty named volume, `lake-metrics-disk`, instead: Docker's local volumes sit on the
same VM filesystem, so `os.statvfs` returns the same numbers with none of MinIO's files in reach.
The review suggested MinIO's own disk metrics; those need either public metrics
(`MINIO_PROMETHEUS_AUTH_TYPE=public`, which shows bucket usage to every container) or a token signed
with the root secret that must change whenever root does. The empty volume adds no surface. That
both volumes report the same filesystem is a rehearsal check.

### 7. Root, last

Rotated user and password, once nothing but `minio` and `lake-init` holds root: a new pair in `.env`
(`make env`'s generator), `minio` recreated (S3 down about 15 s), `lake-init` run. `check-env.py`
then passes and `make up` works again on this host.

### 8. For ADR-044's Outcome, when implemented

ADR-044's "today Trino holds the root keys" is no longer true (section 4); `lake` is read-only twice;
"the storage-level second layer" arrives for Trino as a whole, and per-identity keys stay with P5;
Lakekeeper stays `allow-all`, with ADR-053's guards and this refusal as what holds; the
table-procedure gap (any Trino user can roll a domain table back) is unchanged, with ADR-053's window
and ADR-052's copy bounding what it can lose. ADR-028 section 8 stays a non-goal: no TLS, secrets in
`.env`, and a local user with Docker access is root on this machine.

### 9. What must be proven before this ADR can be accepted

On ADR-052's rehearsal stack (a throwaway compose project with its own network, its own volumes and
small memory limits), each with its printed output:

- **R1** the permission matrix: every key against every prefix for get, put, delete and version
  erase equals section 1; on the live bucket, the same matrix by deletes of names that do not exist
  (204 when allowed, 403 when refused) and puts of `_probe/` names that root removes.
- **R2** Lakekeeper 0.13.9 refuses, on `storage-credential`, a key that cannot write, keeps the old
  one, then accepts `k2-lakekeeper`.
- **R3** with signing off: no signer in the table config; Spark appends and commits with `k2-spark`;
  a write killed mid-way fails on its own error, not on a refused clean-up; the real
  `maintenance.py` compacts, expires and removes orphans with `k2-maintenance`.
- **R5** a forced drop of a pinned table: Lakekeeper's purge is refused and every file stays current;
  `register` brings the table back.
- **R8** root rotated mid-rehearsal: R3 and R5 still pass, the old pair is refused, every user
  still works.
- **R14** (the review's S3) for every non-root key: `DeleteObject` with a `versionId` and a
  multi-object `DeleteObjects` naming versions are both refused; versioning, lifecycle and policy
  changes answer 403; the key cannot create an access key or obtain temporary credentials, or, if
  MinIO allows it, removing and recreating the user invalidates both.
- **R15** (the review's S4) `k2-lakekeeper`'s `PutObject` over an existing data file of a pinned
  table answers 403 while its `metadata/` writes succeed; with signing off, a direct `POST` to the
  signer endpoint for `raw.messages` is refused and
  `GET /catalog/v1/{prefix}/namespaces/raw/tables/messages/credentials` returns no credential.

Also, not gating: the rename-then-`up` attack stops at `lake-init` (ADR-053's G4), and
`lake-metrics-disk` reports the same filesystem.

| Step | Change | What breaks, for how long | Verify | Roll back |
|---|---|---|---|---|

## Rationale

MinIO already checks a secret on every request and already supports scoped users (probed, note §2),
so storage is the cheapest layer at which a refusal holds against any caller. Signing must go first
or no other key is used. The pins, not the catalog, name what the catalog's key may never delete,
because the catalog is the thing being guarded against. Root goes last, when nothing that runs
needs it.

## Alternatives Considered

| Option | Why not |
|--------|---------|
| Keep one key and rely on loopback | loopback stops other machines, not this host's processes or any container; the key is the factory default |
| Vended credentials from Lakekeeper (temporary, per table) | needs MinIO's token service, which Lakekeeper does not test against MinIO, and would hand table-scoped keys to any caller while Lakekeeper authorizes everyone |
| A secrets vault | a new always-on service whose unseal secret sits on the same disk, while the Docker socket already reads every container's environment |
| Per-domain Trino keys now | no separation a person cannot steer around until Trino authenticates (section 4) |
| Rotating a key by changing its secret | can leave minted access keys and temporary credentials valid (S3) |

## Consequences

**Easier:** a leaked engine key exposes one job; the catalog's key cannot destroy the irreplaceable
files; `make up` works again once root rotates.

**Harder:** every new consumer needs a key and a policy line; rotating a key is a remove and recreate.

**Committed to:** MinIO users and policies as the storage refusal; signing off; the pins as the
source of the refusal.

**Risks:** a policy mistake stops a writer until rolled back; anything holding root or the Docker
socket is unaffected by all of this.

**What is not yet verified:** R1, R2, R3, R5, R8, R14 and R15; the `Deny` statement's behaviour on
the pinned MinIO release; whether MinIO users can mint access keys or temporary credentials by
default.

**Revisit when:** any of section 9's lines fails (redesign, then review); Trino authentication lands
(per-domain keys); a Lakekeeper release authenticates without an external identity provider, or
tests vended credentials on MinIO; the platform moves to AWS.
