## Scope

- `notebooks/` uv project (duckdb ≥1.4 w/ iceberg ext, pyiceberg ≥0.9, polars, matplotlib, jupyterlab); `01_connect`, `02_book_at_time`, `03_asof_trades_book` (DuckDB ASOF JOIN), `04_completeness_audit`; `make notebooks`; README notes host→minio resolution.
- 24h burn-in; publish numbers table (`docs/operations/performance.md`): msg/s per stream, gaps/24h, Kraken checksum pass rate with denominator, resyncs, duplicate rate (count vs count FINAL), exchange→recv p50/p95/p99 with n, recv→CH p99, recv→lake p99, bytes/day per table + compression, CPU/RSS per service vs limits (all 17), `hot.ohlcv` 1h/1d/7d p50/p99, FINAL overhead ratio, DuckDB scan timings, time to rebuild `hot.*` from lake.
- **Capacity model, measured column.** Fill `docs/architecture/capacity-model.md` (written predicted-only in Phase C) with `measured` and `error %` columns from the 24 h burn-in, each cell citing the command. Predictions are not edited to match; a row that was 3× out stays on the page with its error, and the wrong assumption is named in one line under the table. Wire the same numbers into the ADR-010 outcome update rather than restating them.
- **Three SLOs with error budgets.** `docs/operations/slos.md`: capture freshness (age of `k2_capture_last_message_ts_seconds` per stream), lake ingest lag (`k2_lake_ingest_lag_seconds`), hot-tier query latency (`hot.ohlcv` p99 over a 7-day window). Each carries an objective, the measurement window, the error budget in minutes/month it implies, and what spending the budget forces (freeze the tier's changes until it recovers). `docker/prometheus/rules/slo-alerts.yml` implements multi-window burn-rate alerts per SLO (fast 1 h/5 m, slow 6 h/30 m) — burn rate, not a bare threshold, so a brief blip does not page and a slow bleed does. Each alert's `runbook_url` resolves to a runbook written in this phase (`capture-gap-recovery.md`, `lake-recovery.md`, `clickhouse-rebuild-from-lake.md`), and the SLO panel row lands in `k2-lake.json` / `clickhouse-overview.json`.
- **Post-mortem of the v2 OHLCV bug.** Publish it on the **audits** surface, not runbooks: `docs/audits/<date>-ohlcv-correctness.md`. The audits README defines a `BLOCKER` as "a live correctness bug" and requires the verdict-first, `severity | file:line | claim | reality | fix` shape, immutable after publication — which is exactly this artefact; runbooks are operational procedures with a measured MTTR, and there is no procedure here, the fix was a schema change. Content: what the docs claimed, what `SummingMergeTree((volume, quote_volume, trade_count))` at `docker/clickhouse/ddl/01-k2-schema.sql:178` actually did to `open`/`close` across a merge boundary, how long it was live, why no test caught it (no test crossed two insert blocks), the detection that would have caught it, and the two guards that now exist — the Phase E CI regression test over two blocks and ADR-026. Blameless: the failure is the missing test and the engine choice, not a person. Add its index row to `docs/audits/README.md`, and cite it from `MIGRATION-JOURNEY.md` as the centrepiece of the v3 narrative.
- **Release automation.** The `/release-check` fresh-clone gate runs before the tag — clone to a temp dir, stack up from nothing, smoke every tier, `make test`, forbidden-string and link sweeps. Its output is the tag's evidence; no separate release doc.
- Resource budget v3 (target ≤13.6 CPU / ≤23 GB steady): clickhouse 4/8G (cpuset 0-3), redpanda 2/2G, spark 1.5/3G, prometheus 1/2G, minio 0.5/1G, prefect-db 0.5/1G, prefect-server 0.5/1G, prefect-worker 0.5/512M, grafana 0.5/512M, console 0.25/256M, lake-metrics 0.1/128M, lakekeeper 0.25/256M, capture ×3 0.25/256M (coinbase 512M, cpuset 12-14); Kotlin removed. Update ADR-010 outcome.
